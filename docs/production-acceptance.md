# Production-oriented account acceptance

This is the independent acceptance plan for the phase beginning at `d3aeefd` on 17 October 2026. It supersedes the earlier blanket deferral of account authentication, adult privacy controls, notification delivery infrastructure and optional bounded AI explanations. Real source feeds remain deferred. Passing local tests is not evidence of real email delivery, verified age, legal approval, production deployment, external-provider reliability or a successful student pilot.

Only synthetic adult accounts, disposable local databases and explicit local test transports may be used during verification. Tests must not obtain credentials, call external providers, send messages, create real accounts or admit real student data. Production configuration is inspected and exercised with rejection probes; provider success cases use the same application boundaries with injected test transports. The HTTP suite also runs a fully configured production-mode process bound only to loopback, supplies its canonical Host/Origin headers on the wire, and verifies empty supply and secure cookie attributes. That is a local reverse-proxy simulation, not a TLS or deployment test. An empty production catalogue is a correct state.

## Evidence rules

- `demo` retains visibly synthetic selectable personas and cannot accidentally become account production mode. `test` uses durable account authentication on loopback with local transports only. `production` requires explicit valid configuration and fails closed when requirements are missing; it must not silently use demo personas, fixtures, identity secrets or test transports.
- Planned independent HTTP and browser suites are `scripts/test-production-http.mjs` and `scripts/test-production-browser.mjs`, on isolated ports 3110 and 3111. Run only after the integration owner confirms the production build is stable. Every run owns its temporary database and child processes.
- A successful response is evidence only when persisted state and a separate read confirm the intended effect. Failure tests verify that state did not change. Matching, consent, delivery and deletion tests use at least two independently authenticated owners and an operator.
- Browser checks use real controls and real application responses. Delayed-response tests may hold actual server responses; deliberate error responses test recovery only and must not stand in for successful product output.
- Completion evidence is written under `docs/evidence/production-*.json` only after the relevant assertions pass. Screenshots and video show actual local test mode, identify synthetic content and contain no credentials or token fragments. Cleanup failures are reported separately from assertion results.
- No acceptance row below is marked passed until its implementation and evidence have been independently inspected. Unit tests may supply clock, crash and provider-failure coverage where HTTP/browser tests cannot reliably control those conditions.

## Known contract decisions

- Account IDs are opaque `account-<uuid>`; role is `STUDENT` or `OPERATOR`. Self-registration is student-only. Adult confirmation is self-attestation and is not a verified-age claim.
- Account profile creation requires `privacyConsent: {policyVersion: 'adult-account-v1', adultConfirmed: true, personalization: boolean}` and an age band whose minimum is at least 18. Demo profile rules remain isolated.
- `GET/PUT /api/student/privacy` uses `expectedVersion` and `expectedProfileVersion`. Personalization defaults off; stored matches are denied until explicitly enabled, while the dashboard can remain useful with no matches.
- Profile deletion and account deletion are different actions. Profile deletion retains account identity; account deletion must coordinate the private-data purge with identity removal. Existing global profile revisions prevent stale mutations after recreation.
- Notification state distinguishes queued/leased/retry/accepted/dead-letter/cancelled. A provider acceptance is not a delivery receipt. Student/operator notification DTOs must not expose the encrypted payload.
- Verification and password-reset links use `/account/verify#token=…` and `/account/reset#token=…`, not query parameters. The acceptance harness independently decrypts only its own disposable synthetic encrypted outbox with the key it generated. No HTTP mailbox or auth bypass exists.

## Independent review findings and regression coverage

- The configured demo mode originally allowed durable account handlers even though its capability report disabled them. The central account repository gate now refuses demo mode; account pages render only the shared-persona explanation. HTTP and browser mode checks cover that boundary.
- A security review found that several handlers authorized before awaiting JSON parsing. Revocation while the request body arrived could leave a stale authenticated owner available for work. The repaired handlers authenticate after parsing, and the independent HTTP suite holds real body chunks, revokes the exact session from a second session, then finishes the request. Student privacy, email preferences, AI explanation and operator import must all return 401 with unchanged stored state. AI-specific units additionally check that no provider invocation occurs.
- Notification dispatch now rechecks current student interest as well as eligibility: removing the sole save, or recording withdrawn/attended/not-attended activity, prevents a pending reminder from reaching transport. Applied activity without a save remains an admitted reminder source. The notification tests exercise exact owner/date isolation and this late-change boundary.
- During harness development, Node fetch normalized the supplied Host header and raw DELETE requests omitted a body length. These were harness defects, not application failures. The final HTTP probes use raw loopback HTTP with explicit body lengths, making the origin and streamed-body checks meaningful.

## Targeted security review after the delivered checkpoint

Fresh local reviewers reproduced and repaired three high-severity defects:

1. **Shared authentication denial of service:** malformed/unknown requests could exhaust a global authentication budget and block unrelated accounts. `account-repository.ts` now uses account/action quotas and validates issued tokens before hashing; `account-password.ts` guards available KDF capacity before charging a quota. The bounded registration bucket table is isolated from existing-account authentication. Regression tests exercise unknown probes, full registration capacity, exhausted generic login responses, unrelated-owner admission and deletion/export of rate metadata.
2. **Pre-registration account takeover:** an attacker could choose a password for another person's email, keep an unverified session, and gain a verified session after the real mailbox holder confirmed the link. Verification now replaces the password chosen by the mailbox holder and revokes all old sessions/tokens; the async handler awaits completion and clears the cookie. Regression tests prove both the earlier password and session fail, including token expiry/replacement during hashing and concurrent one-use consumption. The real verification screen collects the replacement password.
3. **Late complaint lost after profile withdrawal:** deleting all outbox rows removed the only provider-ID association; a later authentic complaint could not suppress future recovery mail. `notification-repository.ts` now keeps a minimal expiring correlation independent of the deleted history, including in-flight acceptance. Regression tests cover accepted-before/after withdrawal, suppression of later sends, account deletion, stale leases, retention, schema migration and restore invalidation.

The AI/runtime reviewer found no supported critical/high defect within the documented single application process. An extra-writer race was demonstrated only with an unsupported concurrent application writer; the deployment limitation is explicit. No external API, mailbox, provider credential, deployment or real user data was used. Passing local tests does not certify production security or establish readiness for minors. The launch audience remains pending.

The security follow-up reran **287 unit/contract tests**, strict typecheck, the Next.js production build, **21 account HTTP groups** and **16 account browser groups**. All passed; the browser run recorded zero external requests, CSP violations or page exceptions.
